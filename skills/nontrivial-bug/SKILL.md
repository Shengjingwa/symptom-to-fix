# 非平凡 bug

原因一下子看不出来、需要排查的 bug，按下面 5 段做。
一眼能改的笔误、明确的小修补、纯功能设计，不要走这套。

本文件是路由：何时走这套、何时写方案文件、何时并行出方案、修好后怎么验收。
本机若已经有 `diagnosing-bugs`、`tdd`、`grilling`、`code-review`，诊断 / 红绿 / 产品取舍 / 审 diff 分别按那些 skill 做；没有就按本文件写死的步骤做。不要用 `/goal` 修 bug。

1 和 2 必做。3 只在「原因清楚了，但怎么改还有好几条路」时做；只有一条路也要写短方案文件。4 和 5 必做。

---

## 1. 定范围

仓库里能查到的，自己查：代码、日志、配置、以前的提交。不要问人要这些。

只有「怎样算修好 / 这次不修什么」需要人拍板、且仓库和文档里没有约定时，才问人。拷问只问产品取舍，不问现场事实。有选择题工具就问一句并等回复；没有就在对话里问一句并等。

这一段结束时，会话里要有这四句：

- 现在看见什么
- 期望是什么，实际是什么
- 怎样算修好
- 这次明确不修什么

**完成：** 四句都写出来了。缺一句就还没做完。

---

## 2. 诊断

若已安装 `diagnosing-bugs`：读并执行它的 Phase 1–4（紧循环、缩小、可证伪假设、打点），然后按下面的「停」执行。

否则按这四步做：

1. **紧循环。** 做出一条本轮已经跑过的命令（测试、脚本、curl 都行），针对用户说的那个症状会红，几秒内出结果，重复跑结论一样。偶发先把复现率拉高，不要把「没打红」直接当结束。
2. **缩小。** 每次去掉一块输入、调用或配置，再跑。留下的每一块都必须是会红所必需的。
3. **假设。** 先写下 3–5 条可证伪假设，每条带预测：「如果是 X，改 Y 会怎样」。一次只验证一条，一次只动一个变量。
4. **根因。** 真正的原因必须能讲清楚机制，并且那条已跑过的红命令是因为这个机制才红，不是旁边另一个问题。

**停在根因说清、紧循环仍红。** 这一段不要改生产代码，也不要把失败用例收成正式测试（throwaway harness 可以留着）。

做不出能打红的复现就停。列出试过什么、还缺什么权限或材料。这时不能说已经找到真正原因，也不能往下走。

**完成：** 有一条本轮已经跑过、针对这个症状会红的命令；根因用机制说清；这条红是因为这个机制。

---

## 3. 选路

原因清楚之后，问自己：改法、改哪里、或兼容/发布策略是不是互斥的 2–3 条。这几条不能同时做。

### 只有一条路

主 agent 直接写短方案文件，然后继续。人可以叫停；没叫停就接着做。

### 有 2–3 条互斥路

主 agent 先列出方向（最多 3 条）。每个方向派一个 subagent：

- 只告诉它：真正的原因、第 1 段的「怎样算好 / 不修什么」、它负责的那一个方向
- 不要告诉它别的方向
- 只出方案和风险，不改代码，不做试验实现

每个 subagent 交回来：打算怎么改、为什么能修好、有什么风险、修不到什么。

主 agent 比较优劣，重点写各条的问题；可以提出 subagent 没给过的新办法，但选它之前必须写清它比起前面那些方案差在哪。选定一条，写入方案文件。

分叉时把推荐那条放在前面，问一句：按推荐做，还是停。等这一句。不要空等批准之外的长讨论。

### 方案文件

路径：当前仓库 `.scratch/bug-<slug>.md`（没有 `.scratch/` 就建）。这是后面改代码时唯一按着做的说明。

至少写清：

- 第 1 段那四句
- 根因（机制，以及那条红命令为什么因此才红）
- 缝：第 2 段紧循环所在的边界（后面 tdd 就测这条缝，不要另开一轮空问）
- 选了哪条，为什么
- 没选哪些，为什么不选（一条路则写「无备选」）
- 已知风险，这次故意不处理什么
- 改代码时不能做什么（换一块去改、放宽协议、删测试）

后面只按选中的那条改。

**完成：** 上述路径上有这份文件，且「选 / 不选 / 禁区 / 缝」都在。分叉时人已经回过一句。

---

## 4. 红绿

若已安装 `tdd`：读并执行它。一次一条竖切，不要先堆一批测试再改实现。

否则按这个循环：先写一条失败测试并看见红，再写刚好够绿的实现。一次一条缝、一条测试。不要把能想象到的规格一次写成测试。

第一条测试：把第 2 段那条会红的复现，收成方案文件里那条缝上的正式测试。先写、先跑、必须看见红，再写刚好够绿的实现。

解决方案文件里已经提到的、旁边容易漏的情况，作为后续竖切补，不要一次写完。

- 可以补测试，但不能把已经写下并见过红的测试丢掉
- 不能换一条没写进文件的路，也不能把否决过的做法偷着用

做到一半发现选中的路走不通：停，回到第 3 段改方案文件，再看测试还够不够，然后重新红绿。不要硬绕。也不要因为测试碰巧绿了，就换一套文件里没写的实现。

**完成：** 第一条回归测试先红后绿；第 2 段那条原始命令也绿。

---

## 5. 收尾

在**本轮**跑证据，不要用「应该过了」结案：

1. 再跑第 2 段那条原始循环（未缩小的现场），确认原症状不再出现
2. 清掉诊断打点：搜索 `[DEBUG-`；删 throwaway harness，或挪到明确标了 debug 的位置
3. 审动手之后的 diff（未提交就审工作区）。若已安装 `code-review`，按它审；否则对照方案文件检查：有没有换路、放宽协议、删测试、残留调试代码

未提交就停在工作区。不要自动提交。

**完成：** 本轮命令输出证明：原症状不再出现，回归测试在，调试代码已删，diff 已经对照方案文件看过。

---

## 怎么接

```
1 定范围（四句；事实自己查，取舍才问人）
    → 2 诊断到仍红（有 diagnosing-bugs 就走它的 Phase 1–4）
         ├─ 没有复现：停，要权限或材料
         ├─ 只有一条路：写短方案文件 → 4 竖切红绿 → 5 验收
         └─ 有 2–3 条路：各方向出方案 → 写方案文件并问一句 → 4 竖切红绿 → 5 验收
                                                              └─ 选的路走不通 → 回到 3
```
