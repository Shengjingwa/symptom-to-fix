# 原因不明的 bug

原因一下子看不出来的 bug，按 6 段做。

本文件定义范围、两个中间产物和每段的完成条件。`diagnosing-bugs` 管根因，`tdd` 管 red-green。进入对应阶段前先读依赖 skill 的 `SKILL.md`；文件读不到就算缺失。写明缺哪个，指向 https://github.com/mattpocock/skills 的 `skills/engineering/diagnosing-bugs` 或 `skills/engineering/tdd`，然后停。

6 段都做。第 3、4 段必须分别留下两份中间产物；正式回归测试和修复从第 5 段开始。用户说了「先别改」这类话，就做到第 4 段，交出两份文档后停。

---

## 1. 说清要修什么

仓库里能查到的，自己查：代码、日志、配置、以前的提交。

本段只有「怎样算修好 / 这次不修什么」需要人拍板、且仓库和文档里没有约定时，才问人。产品取舍就是问一句选择题并等回复。

开始时运行 `git status --short`，检查已有 diff 和未跟踪文件；只记录路径和用途，不混进本轮修复。

这一段结束时，对话里要有四句，每句带出处（用户原话、Issue、测试名或仓库文件路径）：

- 现在看见什么
- 期望是什么，实际是什么
- 怎样算修好（一条能看见的事后状态：命令输出或界面现象）
- 这次明确不修什么

**完成：** 四句和出处都能指出；查证路径或命令已记录；开始时的工作区路径与改动摘要已记录。问过人时，还能指出人的回复。

---

## 2. 找到原因

读并执行 `diagnosing-bugs`：

- 做完 `Build a feedback loop`、`Reproduce + minimise`、`Hypothesise`、`Instrument`
- 读 `Fix + regression test` 里的 correct seam 判据：正式测试必须走真实调用链上的同一种 bug；过浅的测试会给假信心
- 把写正式回归测试、修复和清理留到本文件第 5、6 段

复现命令、偶发问题和无法复现时的停止条件都以那份 skill 为准。反馈循环若用测试搭建，只作一次性 harness。这一段停在根因说清、复现命令仍失败。

**完成：** 有一条已运行、能稳定捕获原症状的脱敏复现命令；复现已最小化；3–5 条可证伪假设已排序；成立的根因有探测证据，主要竞争假设有排除证据；每次探测只动一个变量，诊断打点带唯一前缀；根因机制能解释失败。

---

## 3. 写问题与方案文档

先读 `tdd` 的 `Seams: where tests go`。原因清楚后，提出 2–3 条可独立评估、各自能达到验收目标的完整方案。方案必须消除或隔离已经证实的根因机制；只遮住症状的方向写进淘汰项，不算候选方案。

路径：当前仓库 `.scratch/bug-<短名>/problem-and-solutions.md`（没有目录就建）。这是后面选方案、写测试和审改动时共同依据的事实文档。

按这个顺序写：

1. **事实问题：** 第 1 段四句及出处
2. **证据与根因：** 原始复现命令、脱敏失败输出、根因机制
3. **范围与约束：** 受影响范围、已有工作区改动、兼容要求、已知风险、不修范围
4. **候选方案：** 每个方案写改动位置、修复机制、影响面、发布/回滚办法、风险和剩余问题
5. **比较与推荐：** 逐项比较，写推荐方案及理由；其他方案写不选理由
6. **测试 seam：** 写符合 `tdd`、且在真实调用链上可稳定观察行为的 seam；没有 correct seam 时写证据，并指定原始复现命令作回归
7. **禁区：** 只实施选定方案；保持既有协议；保留见过失败的回归测试；不碰开始时已有的无关改动

先用同一组事实评估所有方案。只有方案仍有相互独立的关键未知、且环境支持时，才并行派 subagent 验证；不给它们重复调查根因。

如果只有一条有证据支持的可行方案，不凑数。写出搜索过的方向和淘汰证据，标成「只有一个可行方案」。

把推荐方案和测试 seam 写成同一句问人。用户确认后把回复写进文档；用户尚未确认时标 `待确认`，第 4 段可以继续写计划，第 5 段不能开始。用户明确授权 agent 选择方案和 seam 时，记录这句授权。

**完成：** 文档在；事实、根因和方案都有证据；有 2–3 个可行方案，或有唯一方案的淘汰证据；每个方案覆盖验收目标并列出影响与风险；推荐理由、seam 和确认状态明确。

---

## 4. 写测试文档

路径：同一目录下的 `.scratch/bug-<短名>/test-plan.md`。写正式回归测试和实施修复之前，先把测试用例写全。

每条用例都写：

- 唯一编号和名称
- 它覆盖的验收目标、根因分支或可测试的方案风险
- 优先级和执行级别：`本轮必做` / `扩展`
- 测试层级和 seam
- 前置状态、数据或 fixture
- 输入与操作
- 可观察的预期结果
- 执行命令或人工步骤
- 状态：`planned` / `red` / `green` / `blocked`，以及本轮输出证据

按下面维度逐项盘点。适用的写用例；不适用的写 `N/A` 和理由：

1. 原症状的正式回归用例
2. 触发根因的最小分支，以及推荐方案改变的机制
3. 正常路径和验收目标
4. 边界值、空值、临近输入和容易混淆的变体
5. 错误、超时、取消、重试和失败恢复
6. 状态迁移、顺序、幂等和并发
7. 配置、数据、协议、平台和版本兼容
8. 相邻功能不回退，以及明确不修的范围保持原状

每条验收目标、每个复现条件、推荐方案的每个可测试风险，至少映射到一条 `本轮必做` 用例。发布、回滚等不能靠测试证明的风险，单列验证或缓解办法，不编成测试。仓库的全量测试只能补充这张映射。无法执行的用例标 `blocked` 并写清缺什么证据；本轮必做用例有 `blocked`，验收就不能通过。

**完成：** 文档在；验收目标、复现条件和可测试风险都有本轮必做用例，其他风险有验证或缓解办法；八个维度都有用例或 `N/A` 理由；第一条正式回归用例落在推荐 seam，或文档已证明没有 correct seam 并改用原始复现命令；此时还没有写正式回归测试或实施修复。

---

## 5. 先失败再通过

继续执行 `tdd`。先检查问题与方案文档：推荐方案和 seam 必须已由用户确认，或用户已明确授权 agent 选择两者；否则停在这里等回复。用户确认的方案或 seam 与推荐不同，就先回第 3、4 段更新两份文档。

一次只做一条：先写一个会失败的测试，再写刚好让它通过的实现。

有 correct seam 时，先把第 2 段的复现收成 `test-plan.md` 第一条正式回归用例：写测试、运行并确认因预期原因失败，标 `red`；再写刚好通过的实现，贴输出并标 `green`。没有 correct seam 时，用文档指定的原始复现命令完成同样的 red-green。

然后按测试文档优先级逐条做。验证既有行为的用例可以一开始就是 `green`；用于证明改变行为的测试必须先因预期原因 `red`，再改实现。每次执行后立即更新状态和证据。

做到一半发现选中的路走不通：停，回到第 3 段更新问题与方案文档，再回第 4 段更新测试文档，然后重新先失败再通过。

**完成：** 第一条正式回归有预期原因造成的失败输出和随后的通过输出；原始复现命令已通过；`test-plan.md` 中本轮必做用例全部是 `green` 并有本轮证据。没有 correct seam 时，原始复现命令同时有修复前失败和修复后通过的输出。

---

## 6. 验收

先清理，再针对最终代码跑证据：

1. 清掉诊断打点；删除一次性 harness，或挪到明确标为 debug 的位置。再用唯一打点前缀做字面量搜索（例 `rg -F "[DEBUG-a4f2]"`），直到生产路径无命中
2. 重跑未缩小的原始复现命令，贴出输出
3. 重跑 `test-plan.md` 中全部本轮必做用例，把最终状态和输出证据写回文档
4. 把根因、否决方案和禁区整理成 commit 信息草稿，写在对话里并追加到问题与方案文档
5. 跑 `git status --short`、`git diff` 和 `git diff --cached`；逐个打开未跟踪文件。对照开始时的工作区基线，只审本轮增量；每个增量都要符合选定方案和禁区。改动留在工作区，等人提交

**完成：** 原始复现和全部本轮必做用例都针对清理后的最终实现通过；生产路径没有诊断前缀；本轮每个增量都符合选定方案，开始时的无关改动未被触碰；两份文档已更新；对话里有证据摘要和 commit 信息草稿。`git status` 仍显示本轮改动未提交。
