# 原因不明的 Bug 排查与修复工作流

本工作流专门用于处理**原因不明显、无法一眼看出改哪里的复杂 Bug**。
整个流程分为 6 个严格按序执行的阶段：前 4 阶段负责查清事实、定位根因、制定方案与测试计划；后 2 阶段负责测试驱动修复与最终验收。

## 核心原则与依赖

1. **先查证，后动手**：在拿到确凿根因、确定方案并列全测试计划之前，严禁修改任何生产代码。
2. **两份关键文档**：第 3、4 阶段必须分别在 `.scratch/bug-<短名>/` 下生成方案文档与测试文档。
3. **尊重「先别改」**：如果用户要求「先别改代码」或「先排查定位」，执行到第 4 阶段生成文档后即刻停止。
4. **外部技能依赖**：
   - 第 2 阶段依赖 `diagnosing-bugs`（用于建立复现与定位根因）。
   - 第 3、5 阶段依赖 `tdd`（用于确定测试切入点与红绿循环）。
   - 如果对应技能不存在，给出安装源（https://github.com/mattpocock/skills 下的 `skills/engineering/diagnosing-bugs` 或 `skills/engineering/tdd`）并立即停止。

---

## 阶段 1：确定问题范围（说清要修什么）

### 目标
把模糊的报错描述转化为清晰、可验证的事实，并锁定本次修复的边界。

### 操作步骤
1. **排查已有信息**：优先在仓库中查阅代码、日志、配置文件和历史 Git 提交记录，不要向用户询问仓库里本就能查到的信息。
2. **记录工作区初始状态**：运行 `git status --short`，记录当前已有的修改和未跟踪文件，确保本轮修复不会夹带无关改动。
3. **必要时向用户确认**：只有在「修到什么程度算修好」或「这次哪些不修」缺少约定且影响判断时，才向用户提问（使用单选/多选题形式）。
4. **总结四句事实**（每句必须附带出处，如用户原话、Issue 链接、测试用例或文件路径）：
   - **当前看到的现象**：报错信息、异常表现。
   - **期望与实际的差距**：原本应该发生什么，实际发生了什么。
   - **修好的验收标准**：一条具体可见的结果（例如某条命令执行成功、界面恢复正常）。
   - **本次明确不修的范围**：防止修复范围随意发散。

### 完成标准
- 对话中明确列出带有出处的四句事实。
- 记录了排查使用过的命令、文件路径以及开始时的工作区 Git 状态。

---

## 阶段 2：定位根本原因（只排查，不改代码）

### 目标
通过最小化复现与单变量验证，用代码层面的机制彻底解释 Bug 的成因。

### 操作步骤
1. 读取并执行 `diagnosing-bugs` 技能中的以下环节：
   - **建立反馈循环**：写出一条脱敏、可重复运行、且当前必定失败的**最小复现命令**。
   - **提出假设**：按可能性排序列出 3–5 个可验证的假设。
   - **打点探测**：每次探测只改变一个变量；所有临时诊断日志必须带唯一的识别前缀（例如 `[DEBUG-abc1]`）。
   - **验证与排除**：拿到证明真实根因成立的代码证据，同时拿到排除其他假设的证据。
2. 确定测试切入点（Seam）：理解 `diagnosing-bugs` 中关于切入点的要求（测试必须覆盖真实调用链路，不能只写浅层测试造假象）。
3. 本阶段严格禁止编写正式业务代码或正式测试，临时验证脚手架仅作为一次性工具。

### 完成标准
- 拥有一条能稳定复现失败的脱敏命令。
- 证明了唯一的根本原因，且根因机制在逻辑上能完整解释失败现象。
- 此时复现命令依然处于失败状态。

---

## 阶段 3：编写问题与方案文档

### 目标
整理排查结论，提出多个可行方案供选择，并明确测试切入点。

### 操作步骤
1. 读入 `tdd` 技能中的 `Seams: where tests go` 部分。
2. 在仓库中创建文档：`.scratch/bug-<短名>/problem-and-solutions.md`。
3. 文档按以下 7 项顺序编写：
   - **1. 事实问题**：阶段 1 的四句事实及出处。
   - **2. 证据与根因**：复现命令、失败输出、代码层面的根因机制。
   - **3. 范围与约束**：波及范围、现有工作区改动、兼容性要求、已知风险、不修范围。
   - **4. 候选方案**：列出 2–3 个可独立行通的完整方案（每个方案写清改动位置、修复机制、影响范围、回滚方案与剩余风险；只掩盖症状的投机方案直接归入淘汰项）。如果确实只有 1 个可行方案，需详细记录其他被淘汰方向的证据，严禁凑数。
   - **5. 方案对比与推荐**：对比各方案优劣，给出推荐方案及推荐理由，写明未选方案的原因。
   - **6. 测试切入点（Seam）**：指定能在真实调用链上稳定观察修复效果的测试层级与位置。若实在无法构造合适 seam，说明原因并指定原始复现命令作为回归手段。
   - **7. 实施禁区**：严格仅执行选定方案；保留原有接口协议；不删除见过失败的测试；不修改开始前已有的无关文件。
4. **向用户提问确认**：将推荐方案和测试切入点汇总为简明描述向用户确认。
   - 用户确认后，将确认记录写入文档。
   - 用户尚未确认前，文档标记为 `待确认`（此时可继续编写阶段 4 的测试文档，但严禁进入阶段 5 编码）。
   - 若用户已明确授权由 Agent 决定，则记录该授权。

### 完成标准
- `problem-and-solutions.md` 文档已创建且内容完整。
- 方案对比清晰，推荐理由明确，切入点（seam）合理，用户确认状态已标注。

---

## 阶段 4：制定全面测试计划

### 目标
在写代码前全面盘点测试用例，确保修复彻底且不引入次生问题。

### 操作步骤
1. 在相同目录下创建文档：`.scratch/bug-<短名>/test-plan.md`。
2. 围绕以下 8 个维度逐项梳理用例（不适用的维度必须注明 `N/A` 及原因）：
   1. **原症状回归**：证明原始 Bug 已修复的正式用例。
   2. **根因最小分支**：触发根因机制的核心分支与边界。
   3. **正常路径**：功能在常规输入下的完整验收目标。
   4. **边界与异常值**：空值、临界值、畸形输入、易混淆格式。
   5. **错误与容灾**：超时、网络中断、取消、重试、错误恢复。
   6. **状态与并发**：状态机迁移、执行顺序、幂等性、并发争用。
   7. **环境与兼容**：数据格式、接口协议、跨平台或版本兼容性。
   8. **周边防回退**：邻近模块功能不受影响，明确不修的范围保持原状。
3. 每个用例必须包含：
   - 编号与名称。
   - 覆盖的目标（对应验收目标、根因分支或方案风险）。
   - 优先级：`本轮必做` / `扩展`（每条验收目标和复现条件必须至少对应一条 `本轮必做`）。
   - 测试层级与切入点（seam）、前置条件与测试数据、操作步骤、预期结果。
   - 执行方式（命令或人工步骤）。
   - 当前状态（`planned` / `red` / `green` / `blocked`）与执行证据。
4. **检查阻断条件**：如果用户要求了「先别改代码」，到此交付两份文档并停止。

### 完成标准
- `test-plan.md` 文档已创建且覆盖全部 8 个维度。
- 所有验收目标和方案风险均已映射到「本轮必做」用例中。
- 第一条正式回归用例已明确对应推荐切入点。
- 此时尚未编写任何正式业务代码或正式测试代码。

---

## 阶段 5：测试驱动修复（先失败，再通过）

### 目标
严格遵循 TDD（红绿循环），先写出必定失败的测试，再编写刚好让其通过的代码。

### 操作步骤
1. **前置门禁检查**：检查 `problem-and-solutions.md`，确认推荐方案与切入点已获得用户确认（或得到明确授权）。未确认则在此等待。如果用户选择了非推荐方案，先返回阶段 3 和 4 更新文档。
2. **第一条回归测试红绿循环**：
   - 在推荐切入点编写第一条正式回归测试。
   - 运行测试，确认其**因为预期的根因原因而失败**，并在测试文档中标记为 `red` 且贴出失败输出。
   - 编写最小化的修复代码，让测试刚好通过，在测试文档中标记为 `green` 且贴出通过输出。
3. **逐条推进其他用例**：
   - 按照优先级依次执行 `test-plan.md` 中的用例。
   - 验证既有行为的用例可以直接为 `green`；验证新增或改变行为的用例必须先 `red` 再 `green`。
   - 每次执行后实时更新测试文档中的状态和终端输出证据。
4. **方案受阻处理**：如果实现过程中发现选定方案不可行，立即停止，返回阶段 3 重新评估方案并更新测试计划后再继续。

### 完成标准
- 第一条正式回归测试拥有「预期失败输出」与「修复后通过输出」的双重证据。
- 原始复现命令与所有「本轮必做」用例全部变为 `green`，且均附带运行结果证据。

---

## 阶段 6：清理、复验与交付

### 目标
清理所有临时调试痕迹，完成最终代码复测，审查改动并生成提交草稿。

### 操作步骤
1. **彻底清理诊断痕迹**：
   - 删除所有阶段 2 引入的临时诊断打点与脚手架。
   - 使用调试前缀在项目中做全局文本搜索（例如 `rg -F "[DEBUG-abc1]"`），确保生产代码中无任何残留。
2. **最终全量验证**：
   - 重新运行未经简化的原始复现命令，确认通过并记录输出。
   - 重新运行测试文档中的全部「本轮必做」用例，确认全部通过并将最终状态写回 `test-plan.md`。
3. **审查工作区增量**：
   - 运行 `git status --short` 和 `git diff`，对照阶段 1 记录的初始状态，逐一审查本次新增的代码改动。
   - 确认所有改动均在选定方案与允许范围内，未触碰任何初始无关文件。
4. **输出总结与 Commit 草稿**：
   - 将根本原因、被否决的方案、测试结果整理成 Commit 描述草稿。
   - 将 Commit 草稿呈现在对话中，并追加到 `problem-and-solutions.md` 文档末尾。
   - **所有改动保留在工作区，等待人工审查和提交，禁止自动 commit**。

### 完成标准
- 生产代码无任何诊断打点残留。
- 原始复现命令与所有必做用例在最终代码上全部通过。
- 工作区改动清晰且完全符合方案范围，两份文档均已完成最终更新。
- 对话中输出了完整的修复摘要与 Git Commit 建议草稿。
