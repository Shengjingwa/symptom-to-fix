# 原因不明的 bug

原因一下子看不出来的 bug，按下面 5 段做。

这份文件只管两件事：什么时候交给哪个 skill，和每段过不去就不许往下走的条件。
`diagnosing-bugs` 管找到原因，`tdd` 管先失败再通过。每次交接前先把那份 skill 的 `SKILL.md` 读出来，读到了才算装上——列在可用 skill 列表里但读不出来（例如指向空目录的链接）同样算缺。缺了就写明缺哪个，指向 https://github.com/mattpocock/skills 的 `skills/engineering/diagnosing-bugs` 或 `skills/engineering/tdd`，然后停。

5 段都做。第 3 段里只有「比较多条互斥改法」是可选子步骤；只有一条路时写短版改法说明，接着做。正式测试和改生产代码从第 4 段开始；用户说了「先别改」这类话，就做到第 3 段停在改法说明，拿到往下改的许可再做第 4、5 段。

---

## 1. 说清要修什么

仓库里能查到的，自己查：代码、日志、配置、以前的提交。

只有「怎样算修好 / 这次不修什么」需要人拍板、且仓库和文档里没有约定时，才问人。产品取舍就是问一句选择题并等回复。

这一段结束时，对话里要有这四句，每句带出处（用户原话、Issue、测试名、或仓库文件路径）：

- 现在看见什么
- 期望是什么，实际是什么
- 怎样算修好（一条能看见的事后状态：命令输出或界面现象）
- 这次明确不修什么

**完成：** 对话里能指出四句原文和各自出处，以及为查这四句跑过的路径或命令。问过人时，还能指出人的那句回复。

---

## 2. 找到原因

读并执行 `diagnosing-bugs` 的 Phase 1–4，做到 Phase 4 Instrument 结束。同一份文件里，接着把 Phase 5 Fix + regression test 的前三段读完（末段是「**If no correct seam exists, that itself is the finding.** Note it.」），拿到 correct seam 的判据：测试要走到真实调用链上的同一个 bug 形态，过浅会给假信心。Phase 5 里「If a correct seam exists」那 5 步和 Phase 6，由本文件第 4、5 段接着做，这一段不做。Phase 1 若用测试当复现，只作一次性 harness。

复现命令什么样、偶发怎么办、做不出来怎么停，都按 Phase 1 那几节的原文，本文件不另立标准。这一段停在根因说清、复现命令仍失败。

**完成：** Phase 1 的 Completion criterion 四条勾完，含贴出调用和脱敏输出（按同一份文件的 Redact 一节脱敏）；Phase 2 的最小化做到每块都去不掉；Phase 3 那 3–5 条排序过的假设列出来过；Phase 4 每条探测对得上一个预测、一次只动一个变量、打点带唯一前缀。根因写成机制，并写明这条失败是因为这个机制。

---

## 3. 定改法

原因清楚之后，问自己：改法、改哪里、或兼容/发布策略是不是互斥的 2–3 条。

路径：当前仓库 `.scratch/bug-<短名>.md`（没有 `.scratch/` 就建）。这是后面改代码时按着做的改法说明。

至少写清：

- 第 1 段那四句（含出处）
- 第 2 段那条复现命令的原文，和它脱敏后的失败输出
- 根因（机制，以及那条复现命令为什么因此才失败）
- 测试挂在哪个接口上（`tdd` 里叫 seam），以及这个接口是人确认过的还是「未经确认」
- 选了哪条，为什么
- 没选哪些，为什么不选（一条路则写「无备选」）
- 已知风险，这次故意不处理什么
- 禁区：只按选中的那条改；协议按原约定执行；已经写下并见过失败的测试留着；改动留在工作区，等人提交

### 只有一条路

写短版改法说明，把测试挂在哪个接口上写进去，标「未经确认」，接着做。在对话里说明按的是哪条路、哪个接口，人可以叫停。

### 有 2–3 条互斥路

列出方向（最多 3 条）。每个方向派一个 subagent，只给真正的原因、第 1 段「怎样算好 / 不修什么」、这一个方向。各自交回：怎么改、为什么能修好、风险、修不到什么。主 agent 比较时重点写各条的问题；提出新办法前必须写清它比前面差在哪。选定后写入改法说明。

把推荐的改法和测试挂在哪个接口上写成同一句问人：按推荐做，还是停。人回了就把这句回复写进改法说明；人 AFK 就按推荐走，标「未经确认」——和 `diagnosing-bugs` Phase 3 对 AFK 的处理一致。

**完成：** `.scratch/bug-<短名>.md` 在，上面「至少写清」那张清单每条都有内容，接口那条注明是人确认过还是「未经确认」。

---

## 4. 先失败再通过

读并执行 `tdd`。它要求写测试前先写下接口、并跟人确认（"No test is written at an unconfirmed seam."）。第 3 段已经把接口写进改法说明，「写下」这一半成立。「确认」这一半看改法说明里那一行：人确认过的，这条规则已经满足，不再问第二次；写着「未经确认」的，这条规则没满足，本文件在这里开一个例外——仍照那个接口写测试，那句话留着，人看见可以叫停，叫停就回第 3 段。`tdd` 其余部分照做。

一次只做一条：先写一个会失败的测试，再写刚好让它通过的实现。

第一条测试：把第 2 段那条会失败的复现，收成改法说明里那个接口上的正式测试。先写、先跑、对话里贴出失败输出，再写刚好让它通过的实现，再贴通过输出。

改法说明里已经提到的、旁边容易漏的情况，作为后续的「一次只做一条」补。

找不到合适接口时（`diagnosing-bugs` Phase 5 那条成立）：把这个结论写入改法说明，用第 2 段那条复现命令做先失败再通过。

做到一半发现选中的路走不通：停，回到第 3 段改改法说明，再看测试还够不够，然后重新先失败再通过。

**完成：** 对话里有第一条正式测试的失败输出和随后的通过输出，以及第 2 段那条原始复现命令的通过输出。找不到合适接口时：改法说明里有这句结论，且原始复现命令有失败输出和随后的通过输出。

---

## 5. 验收

在本轮跑证据，且这几条都要在最后一次改代码之后跑：

1. 再跑第 2 段那条未缩小的复现命令，确认原症状不再出现，贴出输出
2. 用本轮那个唯一打点前缀做字面量搜索（例 `rg -F "[DEBUG-a4f2]"`）清掉诊断打点；删一次性 harness，或挪到明确标了 debug 的位置
3. 跑 `git status --short` 列出全部改动路径，再跑 `git diff` 和 `git diff --cached`。新建还没跟踪的文件两个 diff 都不显示，逐个打开看。全部逐条对照改法说明里的禁区
4. 把根因（哪条假设成立）、否决过的改法、禁区整理成一段 commit 信息草稿，写在对话里并追加到改法说明末尾，供人提交时用。改动留在工作区，等人提交

**完成：** 对话里有：本轮原始复现命令的通过输出；那个唯一前缀的搜索结果（生产路径无命中）；`git status --short` 和两条 diff 的输出，未跟踪文件的内容也看过，且每个改动能对上改法说明、禁区未破；一段可直接用的 commit 信息草稿。`git status` 仍显示这些改动未提交。
